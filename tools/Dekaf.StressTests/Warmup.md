# Producer warmup and measurement boundaries

Duration-based producer scenarios use `--producer-warmup-seconds` (default 180, minimum 20). The default allows longer continuous load in each reuse cycle. Assess its sufficiency from throughput and latency trends; JIT activity is not an acceptance metric. Declare the same duration for every A1/B/A2 process before a comparison. Warmup does not extend individual phases until they look good. If startup affects the measured performance, the experiment is inconclusive; investigate it and predeclare a revised campaign.

`ProducerWorkload` runs the same producer loop, delivery-latency sampling, resource reporting, allocation sampler and runtime observers in warmup and measurement. The producer stays alive across six load/drain cycles and measurement. Payload size, rotating key distribution, compression, acknowledgements, batching, connection policy and synchronous-versus-awaited delivery behavior match the measured workload. Drains exercise object return and reuse at the workload's actual concurrency. This primes the working pool demand; it does not prove that every internal pool is at its maximum capacity. Artificially filling every pool would create a different workload.

Warmup traffic and counters are separate from measurement. Each Dekaf fire-and-forget cycle observes topic-filtered delivery errors on its own throughput tracker and rejects failed delivery before another cycle can start. Measurement error observation begins only after successful warmup and remains active through producer disposal. Each cycle must run its full declared load duration and complete without reported errors. Drain time is recorded separately from active workload time. The broker watermark check establishes the post-warmup starting offset after all warmup traffic drains. No forced collection follows warmup. The same pre-touched latency histogram is reused across all six warmup cycles and measurement. Its buckets, outliers, counters and delivery-drain completion are reset before each phase starts, so warmup-only large arrays cannot become measurement-time garbage. Reset requires all previous delivery samples to be drained. Sampled delivery callbacks finish before measurement stops; their tasks are not retained in a growing collection. The duration timer stops ingress, while runtime sampling continues through final delivery drain.

An awaited send may still be awaiting acknowledgment at the ingress deadline. The controller stops waiting for ingress and enters drain while retaining that send's task. It records the real delivery result and latency before stopping measurement. Canceling the send immediately would lose its result when cancellation follows append, even though the message can still arrive at the broker. For fire-and-forget workloads, the first flush can release buffer admission; a second flush after the produce loop finishes drains any message appended after the first flush. Both flushes, final admission and sampled callbacks share one 30-second drain deadline; the second flush receives only the remaining time. A drain deadline returns a failed diagnostic result containing `FlushTimeout` or `DeliveryDrainTimeout`, any earlier errors, counters and runtime samples. The flush timeout and shared drain cancellation can expire in either order. It cannot become a successful measurement. Explicit caller cancellation still propagates. Late failures from a producer or flush that ignores cancellation are observed. This applies identically to Dekaf and Confluent.

Results retain process-wide thread-pool size/backlog, CPU time, allocated bytes, GC counts/pause duration, managed heap and working-set observations. These include harness work; they are not isolated client CPU or allocation measurements. See the [.NET runtime metric definitions](https://learn.microsoft.com/en-us/dotnet/core/diagnostics/built-in-metrics-runtime). The warmup/runtime validator requires complete coverage, a final ten seconds of active warmup without thread-pool size changes, and no such transitions inside measurement. Missing coverage, startup transitions or mismatched warmup durations yield `INCONCLUSIVE`; samples and maxima are never trimmed. A quiet counter series is a necessary check, not proof of statistical equivalence or long-run stability. Investigate JIT manually with standard tools in a separate diagnostic run; missing JIT logs or compilation activity alone does not invalidate benchmark results.

The current validator cannot establish steady state for completed-message throughput, CPU per completed message, pending work, allocations per completed message, heap/working set, GC activity, or delivery latency over time. Runtime counters are recorded, but temporal assessment is not implemented; interval delivery-latency distributions and continuous completed-message counts are also missing. A `coverageVerdict` of `VALIDATED` reports only coverage and thread-count checks. The overall verdict remains `INCONCLUSIVE`, exits nonzero, and blocks comparison acceptance and history publishing for every current producer result. This is an explicit missing-evidence condition, not a measured regression. Repeating the same aggregate schema cannot fix it. Completing this gate requires representative interval evidence and a predeclared assessment of all these trends; no samples may be trimmed and no arbitrary tolerances or external pass flag may substitute for that work. Scheduled workload selection and raw artifact retention remain unchanged.

The exact-SHA stress workflow uses one `ubuntu-latest` VM, with brokers on CPUs 0–1 and the client on CPUs 2–3. Both products compile the candidate harness and tools-scoped props, while product sources and root build inputs remain pinned to their own revisions. Root package/compiler/SDK/NuGet configuration must match for this shared fixture; differences stop the workflow before measurement and require a dedicated fixture. The workflow never copies candidate root build inputs onto the baseline to make a comparison pass. A fresh-main ancestry check, build-server shutdown, and separate one-minute correctness runs for both fixtures precede A1/B/A2. Every process creates fresh Testcontainers brokers, including single-broker lanes. Provenance records product/harness SHAs, runtime and runner settings, fixture adaptation, binary hashes and main at the end. The paid scheduled lanes retain their runner selection and coverage.

The A–B–A comparison report is generated even when warmup validation fails. With `--require-startup-assessment`, the comparator assesses the same parsed phase results, preserves absolute metrics, deltas, control drift and uncertainty, and labels those metric classifications as diagnostic. Incomplete startup assessment keeps the overall verdict `INCONCLUSIVE` and the exit code nonzero; producing a report does not authorize acceptance.

Producer job timeouts include each measured duration, the requested warmup for each client sample, seven 30-second drain allowances per sample, and 15 minutes for builds/broker setup/teardown/reporting. Exact-SHA comparisons also include both one-minute validation runs and their warmups. Existing larger budgets are retained. A 30-minute A1/B/A2 with 180-second warmup reserves 140 minutes; adding B2 reserves 176 minutes. A regular 30-minute single-client sample reserves 52 minutes; the full six-sample producer shape reserves 234 minutes. Requests exceeding the [GitHub-hosted six-hour job limit](https://docs.github.com/en/actions/reference/limits) fail selection before starting the measurement job. Runner selection, selected lanes, measured durations, and sample counts are unchanged.

Scheduled and ordinary manual duration-based producer runs validate every client result in every result file, including paired, 3-connection and adaptive variants. The expected count comes from the selected matrix shape; a missing sample cannot silently pass. Any missing coverage or startup transition makes the lane fail with an archived INCONCLUSIVE validation report. Combined tables remain diagnostic when any lane fails, and trend acceptance and docs/history publishing are blocked. No observed samples or maxima are removed.

This warmup applies to duration-based producer scenarios. Consumer, transactional, round-trip and BenchmarkDotNet workloads require their own representative priming and startup evidence. In particular, BenchmarkDotNet `GlobalSetup` loops do not prove that its generated engine and actual-stage observers are warm. These checks do not replace the protected-metric comparison, hot-path MemoryDiagnoser evidence, or longer stability/recovery/shutdown validation required by `AGENTS.md`.

Producer loops record the client's `KafkaException` and `TimeoutException` as failed operations. Unexpected exceptions fault the workload immediately; they are not swallowed by the send-error counter. Normal ingress cancellation remains distinct from send failure.

The optional `fixed_worker_threads` experiment establishes a live worker pool before warmup. Minimum and maximum limits alone do not prestart workers or prevent idle retirement. For a nonzero request, the workflow sets both limits, disables worker idle retirement, and asks each workload process to start the requested number of workers. Startup rejects mismatched limits, missing retirement configuration, or an incomplete pool. Both controls and candidate use the same setup; input `0` preserves runtime defaults. Synchronization, queued callbacks and provenance allocation occur once per process before warmup, with no extra work in message loops.

Each process retains its actual requested/minimum/maximum/live worker counts in `fixed-worker-pool-<pid>.json` beside its results. `dotnet run -c Release -- check-worker-pool` checks the configured pool across a 25-second idle interval without starting Kafka. It requires `DEKAF_STRESS_FIXED_WORKER_THREADS` plus the corresponding `DOTNET_ThreadPool_ForceMinWorkerThreads`, `DOTNET_ThreadPool_ForceMaxWorkerThreads` (hexadecimal values) and `DOTNET_ThreadPool_ThreadTimeoutMs=-1` environment settings. The normal steady-state validator still rejects changing worker counts; this startup configuration does not waive CPU, allocation, memory, latency, throughput or stability acceptance.
