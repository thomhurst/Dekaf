# Rack-aware follower recovery workload

`consumer-follower-recovery-3b` is a manual-only, Dekaf-only stress lane. It does not expand `all` or published paired runs. Locally, select `--scenario consumer-follower-recovery --client dekaf --brokers 3`.

The harness owns three Kafka brokers. Each workload partition has leader 1 in rack-b and follower 2 in rack-a. The consumer requests rack-a, uses three connections per broker, disables fetch sessions and adaptive connection scaling, and manually assigns every partition from offset zero with `AutoOffsetReset.None`. Topic retention is disabled. Seeding uses `Acks.All`, then the consumer replays the fixed topic without a competing live producer.

Every sixteenth eligible nonempty follower partition response is replaced with `OFFSET_OUT_OF_RANGE`. Metadata, replica selection, network requests and leader responses remain real. Only one fault is outstanding per partition and replay generation. Discarded batches are returned to their pools; their response retains its network memory owner for normal consumer cleanup.

An independent oracle requires consecutive offsets within each partition and rewinds only after every seeded partition is complete. A duplicate, gap, unexpected offset, failed phase, or stalled consumer fails the workload. Every warmup phase requires injected faults, observed leader-response activity and complete replay progress. Measurement additionally requires leader responses at recorded fault offsets. A duration boundary may cancel the last in-flight operation.

The result's `followerRecovery` counters distinguish injected faults, matching leader responses, responses following already verified record progress, complete passes, unmatched leader responses and sequence violations. Matching is diagnostic correspondence, not proof of one-to-one request causality: requests overlap, and replay seeks invalidate outstanding responses. An unmatched response never authorizes a skipped or duplicated record. The maintained [follower-retry integration tests](../../tests/Dekaf.Tests.Integration/ConsumerFollowerOffsetRetryIntegrationTests.cs) separately establish the causal unchanged-offset leader retry for Earliest, Latest and None.

Warmup and measurement use the existing six-cycle consumer runner, allocation sampling, CPU measurement, progress watchdog and resource observers. The sequence oracle adds one constant-time check per record without allocations. Connection wrappers are cached per connection; response inspection and atomic counters run per request/partition response; arrays are reset per replay; result snapshots allocate per phase. All of this harness work is included in the reported process metrics and applied identically to both products in an exact-SHA comparison.

For the prefetch-overlap correction, use `consumer-1b` with `baseline_sha` to compare publication costs under load. The pre-fix product fails this follower lane's strict sequence oracle: `validation-a` stops the workflow before candidate B or control A2 runs, so that pairing cannot establish performance acceptance. The real-broker integration tests and a candidate-only follower run provide separate fault-correctness evidence.

The follower lane supports `baseline_sha` only when both pinned revisions already satisfy the sequence oracle. Otherwise, omit `baseline_sha` for a candidate-only correctness run or select a compatible comparison lane. The workflow overlays identical candidate harness sources onto both pinned products, rejects incompatible root build inputs, and never bypasses a failed baseline validation.
