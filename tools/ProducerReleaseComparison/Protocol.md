# Release comparison experiment

Question: has the single-connection non-idempotent producer regressed against the actual NuGet Dekaf 1.15.0 package?

A is the nuget.org 1.15.0 binary with its resolved dependency closure. B is the pinned candidate project with its own unchanged root build inputs. Fixture source and runtime are identical. The product source tree matches the September 12 linked run; intervening main commits changed the harness and test-only TUnit dependencies. Record all assembly identities, assets, binary hashes, source SHA and environment.

One eight-vCPU VM. Choose a complete two-thread client core using VM-reported CPU/socket/core topology; broker and independent offset observer use all other cores. Record the complete mapping and whether the original 0-5 / 6-7 split shares reported cores. This is not proof of host CPU dedication. Server GC and normal .NET thread-pool/GC adaptation. Fresh Kafka 4.3.1 container and six-partition topic for each process, identical retention/tmpfs settings. No compression, leader acknowledgements, idempotence off, one pinned connection, 5ms linger, 1MiB batch, 512MiB buffer, 10ms delivery target, delivery diagnostics enabled. 1000-byte string payloads and 10,000 preallocated keys. FireAsync with one ProduceAsync latency sample per 1000 messages and yield every 100,000, matching the established lane.

Validate both binaries for 20s after 20s warmup. Then A1, B1, B2, A2, B3, A3, A4, B4: four adjacent pairs balanced in AB/BA order, with both products' mean order position 4.5. Each has 180s representative warmup and 300s measured load; flush and await sampled deliveries, retaining drain duration. The prior four fifteen-minute samples remain the long-duration evidence; this follow-up increases independent process repeats and balances linear time drift. No sample trimming, no process reruns to obtain a preferred outcome.

Record five-second client intervals throughout warmup and measurement: accepted count, sampled delivery latency p50/p95/p99/max/count/overflow, pending sampled deliveries, errors, process CPU, allocations, heap, working set, GC counts/pause duration, thread pool size and pending work. Independent ListOffsets samples provide delivered offsets and backlog evolution, plus exact broker offset totals before/after each process. The independent observer also records /proc/stat per-CPU ticks (including steal) and load average. Compare completed counts to accepted counts and reject delivery loss or errors. Workload adds equal observation overhead to both versions; absolute rates need not equal the original harness.

Assess startup, transitions and interval trends explicitly; do not imply the existing incomplete warmup gate accepted this dedicated experiment. Keep absolute distributions, control/candidate repeat differences and adverse trends visible. Compare all candidate samples against all controls for throughput, CPU, latency, allocations and stability, plus the four adjacent paired log-ratios. Report their geometric mean and a two-sided 95% Student-t interval with 3 degrees of freedom; this is a small-sample estimate conditional on approximately independent paired effects, not a universal bound. Existing aggregate-screen tolerances (3% adverse differences, 10% repeat drift, 1B/message allocation floor) are context only, not a claim of statistical certainty. A repeatable slowdown larger than repeat variation supports regression for this workload; overlapping or unstable repeats leave the result inconclusive. Use process-repeat and time-block variation, not billions of correlated messages, to describe uncertainty. Maximum latency remains informational. This experiment cannot establish all producer configurations or all machines.
