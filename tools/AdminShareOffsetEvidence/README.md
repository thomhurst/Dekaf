# PR #3136 administrative performance experiment

This harness branch is separate from the product PR. Product SHAs are pinned before dispatch.

## Work and boundaries

One GitHub-hosted `ubuntu-latest` VM runs A1 (fresh main), B (PR head), A2 (the same main), sequentially. Both products build and validate before any timed phase. Fixtures are copied byte-for-byte, with only the documented `CANDIDATE` compilation symbol enabling APIs absent on main. No product source is adapted.

The same VM then runs P1 (the immediately preceding product commit), B2 (the same candidate), P2 (the same predecessor), using identical single-group and 32-group positive batch cases, plus default-timeout empty queries in the real and in-memory clients. All three products build and validate before timing. This additional comparison isolates the empty-input correction; it does not replace fresh-main acceptance. The predecessor has the new API, so these cases perform equivalent work. Empty-input zero-deadline behavior differs and is characterized only on B. Both comparisons use the same declared tolerances and retain separate assessments without averaging controls. The earlier +30.91% mean difference between unpaired Windows diagnostics at d619a3f7a and e37ef31a6 remains historical and unattributed; this campaign does not retroactively resolve that different pair.

Controls: existing `DescribeShareGroupOffsetsAsync` loops for 32 groups and one group, plus the existing `InMemoryAdminClient.DescribeShareGroupOffsetsAsync` loop for 32 groups. Each group has one selected stored partition. These methods retain identical inputs and observed results across all phases. Their measured method bodies and async state machines contain no conditional compilation; the cached dispatcher chooses control or candidate-only methods outside the measurement loop. New API construction must not enlarge a control state machine.

Candidate-only characterization: 32-group and single-group batches on v1; a 32-group v0 fallback; a 32-group mixed response with group and partition authorization failures; one transient coordinator error among 32 groups; cancellation triggered during a send; a zero-deadline rejection with no send; and a 32-group in-memory batch query. The new API does not exist on A, and its keyed partial-result contract differs from the existing list-returning loop, so no equivalent-work timing ratio is claimed between those operations. Cancellation and deadline cases count an observed expected terminal exception as a completed administrative attempt; they are separate from successful-query cases. Unexpected errors or missing completions fail validation.

Empty-input cases additionally cover default-timeout real and in-memory queries and zero-timeout real queries. They count a completed empty administrative result as one call and assert no broker send. The `:1` case suffix selects one fixture group before clearing the request map; it does not indicate one requested group for these empty-input cases.

The synthetic connection returns prebuilt wire response objects. Broker/network latency and CPU are excluded. The boundary is public admin method invocation to complete result observation. No message delivery changes: per-message throughput/latency/allocation and producer/consumer sustained load are not applicable; the unit is a completed administrative call. Correctness against Kafka is covered separately by integration CI.

Each fresh probe and BDN process first executes 128 complete measurements of at least 50 ms each and one complete one-second measurement, including result finalization and JSON serialization. It then warms its actual configured workload for **120 seconds** before sampling. Every primer segment and elapsed warmup is retained and validated. The fixed primer count supplements, and does not replace, elapsed workload warmup. The probe measures **60 seconds** at closed-loop concurrency one (next call starts after the previous call completes). There is no queue or dropped offered work. Before the complete-entry primer, BDN additionally warms its generated empty callbacks and measurement formatting for ten seconds and prepares two fixed-stage engine methods outside measured work. The callback guard rejects nonempty or unexpected generated hooks. BDN then measures 12 iterations at 500 ms nominal iteration time, one launch, after its explicit 120-second setup workload warmup and fifty normal workload warmups. The driver requires at least twenty elapsed workload seconds and positive completions from raw BDN warmup measurements; a fixed iteration count alone is insufficient. Explicit smoke is tooling validation only and does not satisfy these acceptance durations. `OutlierMode.DontRemove` preserves every measured iteration in the summary and raw output. All phases use Release/net10.0, workstation GC, tiered JIT and dynamic PGO enabled. No profiling agent is attached.

The six-phase campaign contains 32 probe/BDN configurations, including both product comparisons and candidate-only characterization. Its job limit is 240 minutes to accommodate identical elapsed warmup across every configuration; the normal benchmark publishing matrix remains disabled. No new hosted dispatch is implied by this tooling update.

Probe latency histograms retain every completed call's exact Stopwatch tick count, including maxima; no tail clipping, discarded startup samples, percentile averaging, or sampling is permitted. Histograms preserve the distribution, while one-second rows preserve temporal CPU, throughput, p50/p99/max, GC, heap/RSS, JIT method/time, thread-pool threads/pending work, and completion counts. CPU/allocation scope is the whole probe process, including histogram/counter bookkeeping. MemoryDiagnoser independently records inclusive managed allocation per administrative call. No zero-byte per-message claim is made for allocated admin result objects.

BDN host workload signals and worker monotonic clock origins identify runtime intervals overlapping actual measurement. Signal files include both case and process ID because the OS can reuse a worker PID for a later case. The driver validates their process/frequency identities, ordering and complete runtime coverage. One-second boundary intervals conservatively include adjacent stages and IPC latency; no per-call or per-iteration hooks are added. A zero-valued timing control cannot provide a relative ratio: absolute observations remain retained, and precision is marked missing/INCONCLUSIVE instead of dividing by zero or inventing a ratio.

## Criteria declared before hosted measurement

Correctness requires all expected results and zero unexpected exceptions, timeouts, or leftover asynchronous work. Candidate control throughput must be no more than 3% below **each** baseline; CPU/call no more than 3% higher; p50/p99/max latency no more than 5% higher; allocation/call must not increase beyond a 1-byte measurement allowance. A1/A2 control drift must meet those same bounds. All measurements and absolute deltas are retained even when inconclusive. BDN confidence bounds and per-second sample counts must be reported; overlapping bounds alone cannot prove equivalence.

Warmup is insufficient if the final five warmup seconds or measured series retain material JIT/thread-pool startup transitions or systematic CPU/latency drift. Such cases are INCONCLUSIVE and require a revised experiment across every phase. Heap/RSS/GC series must show bounded repeated-call behavior for this measured interval; this does not establish long-run leak absence. Candidate-only cases characterize cost and correctness, not a Pareto comparison against a nonexistent baseline.

A full PASS requires all applicable control criteria and credible startup/stability evidence. REGRESSION requires a confirmed protected-metric loss; control noise, missing data or insufficient precision remain INCONCLUSIVE. The evaluator emits measurements and a provisional control assessment only; it cannot update a GitHub gate or approve a merge. One exact repeat is the maximum automatic repeat after INCONCLUSIVE, then experiment changes or maintainer direction are required. The original [run 34161413446](https://github.com/thomhurst/Dekaf/actions/runs/34161413446) was cancelled after the shared warmup defect was identified. Its [partial absolute metrics and retention limits](https://github.com/thomhurst/Dekaf/pull/3136#issuecomment-5576172928) remain INCONCLUSIVE. The legacy 32-group control exceeded several candidate loss limits; the new warmup must not be assumed to erase that observed cost. The unpaired Windows single-candidate diagnostics also remain historical and cannot substitute for the controlled comparison.

Retain product/harness SHAs, SDK/runtime, runner image/hardware, all sources, binaries, build/validation/BDN logs, histograms, time series and SHA-256 inventory in the uploaded artifact and durable PR archive.

Each probe and BDN process records the paths and SHA-256 hashes of loaded managed assemblies beneath its application directory before warmup. The driver retains and hash-verifies those assemblies, and preserves generated BDN projects and binaries separately for each phase before another phase can overwrite them. Framework binaries are identified by the pinned SDK/runtime inventory. A missing product identity or mismatched loaded-binary hash fails the experiment.
