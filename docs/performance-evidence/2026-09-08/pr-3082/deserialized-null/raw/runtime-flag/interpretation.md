# Interpretation and next experiment

Acceptance remains INCONCLUSIVE. Every case has runtime compilation or thread-pool transitions across measured boundaries. Normal-case A1/A2 drift ranges from -98.758% to +38.893%. ByteArray and String improve against A1 but are respectively 133.220% and 60.607% slower than A2; those opposing comparisons are not a win. CustomString is 4.185%/5.578% slower with -1.319% control drift, but candidate uncertainty is wide and its first three samples are elevated (10.815907/8.952999/8.621860 ns), with 51 additional compilations reported at the third boundary. All 15 samples remain included; no causal performance loss or equivalence is established by trimming those samples.

Twenty seconds of direct workload warmup did not stabilize the generated BDN execution path. The next experiment needs warmup through the actual BDN workload/engine, an enforced and verified elapsed minimum of 20 seconds there, and method-level attribution of remaining JIT activity. Settings must be fixed uniformly before another A1/B/A2 run. No repeat or additional paid run follows this diagnostic.

The narrow MemoryDiagnoser results and exact 1,000-operation probes are zero in all 27 processes. This establishes only the exercised key construction/hash/equality operations. It does not clear the historical non-zero full-dispatch allocation finding or establish whole-message allocations. All seven internal key layouts are unchanged (16 B reference/array, 8 B int, 12 B int?, 24 B memory/segment).

Process CPU, GC, heap and RSS series describe the complete benchmark host between emitted boundaries, including harness work. BenchmarkDotNet 0.15.8 defaults GcMode.Force to true (retained package XML documentation), so the forced collections between iterations cannot be attributed to per-key allocation or interpreted as application GC behavior. BDN iteration extrema are not actual per-message latency. Fresh-main Ubuntu end-to-end completed-message throughput, CPU/message, p50/p99/max delivery/processing latency and sustained stability remain missing.

A further measurement hypothesis is process-wide single-core affinity: reported compilation-time deltas reach 13.991 seconds for only six new compilations in A1 Int32, while all threads share affinity mask 4. This may delay background compilation while foreground work saturates the selected CPU, but these counters do not establish that cause. A future experiment should measure JIT method/tier transitions and scheduling with a uniformly declared affinity configuration that permits compiler progress; merely increasing an iteration count is not proof of stable execution.
